
## Purpose and status

Design specification for extending [[SSH Keys]] with a new **Public key handler — Debian PRNG lookup** in Step 2. Preserves the deliberated design from the session where the vector was investigated, structural home was reasoned through multiple candidate positions ([[Linux Privilege Escalation Checksheet]] Step 16 narrow-vector, separate walkthrough, Shared Concept, handler-in-existing-walkthrough), and the correct placement was derived from first principles per Vault_Strategy conventions. The build itself is deferred to first real-target encounter — the handler body is unbuilt at time of writing; a stub in [[SSH Keys]] Step 2 currently points at this note.

**Status: build-when-encountered.** The vector applies only when SSH keys generated by an affected Debian OpenSSL package are present on the target (in an `authorized_keys` file, or as standalone `.pub` files). Hit rate is near-zero on modern non-legacy targets. When it fires, the blacklist grep yields the matching private key; whether that private key yields root depends on which SSH principal the compromised pubkey authenticates as (root user's authorized_keys → root direct; non-root user's authorized_keys → lateral foothold; standalone SSH_PUBKEY → pivot lead). Real-target validation is the canonical gate per Vault_Strategy build-when-encountered convention.

## Motivation — what SSH Keys.md currently misses

Current [[SSH Keys]] Step 1 marker priorities treat:

- `SSH_AUTHKEYS: <file>` (public keys authorising SSH login, one per indented line beneath the marker) as **informational only**.
- `SSH_PUBKEY: <file>` (standalone `.pub` files outside authorized_keys) as **informational only**.

No handler in Step 2 fires on either marker. Under standard cryptographic assumptions, that disposition is correct — recovering a private key from its public key is computationally infeasible.

**The Debian PRNG exception:** for public keys generated by affected OpenSSL packages (specifically `0.9.8c-1` up to but not including `0.9.8g-9`) on Debian-family systems in the 2006-09-17 through 2008-05-13 window, the entire private-key space is precomputable and has been publicly precomputed. Any pubkey matching the precomputed set can be exchanged for its private key via a fingerprint lookup — no cryptographic work required. This exception makes the "informational" disposition wrong specifically for pubkeys within this class.

Coverage gap: at time of writing, an operator on a target whose `authorized_keys` contains a Debian-PRNG-weak pubkey has no LPEC-driven route to exploit it. The vector is real but off-path.

## Verified facts — primary sources

Verified during the 2026-08-04 design session.

### Affected package range

**OpenSSL package versions `0.9.8c-1` up to (not including) `0.9.8g-9`** on Debian-based systems. Source: [Debian security-tracker CVE-2008-0166](https://security-tracker.debian.org/tracker/CVE-2008-0166); [DSA-1571](https://www.debian.org/security/2008/dsa-1571).

- **Introduced:** 2006-09-17 (release of `0.9.8c-1` in Debian).
- **Disclosed:** 2008-05-13 (DSA-1571).
- **Fixed versions:** `0.9.8c-4etch3` on Debian etch; `0.9.8g-9` on Debian lenny/sid; parallel fixes in Ubuntu USN-612-1 and USN-612-2.

### Affected distros

- **Debian:** etch, lenny, sid. Sarge NOT affected (Debian security-tracker records the vulnerable code was not present in sarge).
- **Ubuntu:** all releases derived from affected Debian source in the window (7.04 Feisty, 7.10 Gutsy, 8.04 Hardy).
- **Other Debian-derived distros** in the same window (Xandros, Mepis, Knoppix, and others).

### Vulnerability mechanism

Debian-specific patch to `openssl` — attempting to silence a Valgrind uninitialised-memory warning — removed the entropy contribution to the PRNG state. Consequence: PRNG output derives essentially only from the process PID. Linux PID space at the time was `1..32,768`, so the effective seed space collapses to roughly **32,767 unique seeds per (architecture, key type, key size)** combination.

**Consequence for key generation:** every possible RSA/DSA private key that OpenSSL could have generated on an affected Debian system is enumerable in ~32,767 attempts per (arch, keytype, keysize) combination. The full set was precomputed and released by H D Moore and collaborators in May 2008.

### Publicly available exploit tooling

- **`openssl-blacklist` Debian package** — flat text files at `/usr/share/openssl-blacklist/blacklist.<KEYTYPE>-<BITS>` (e.g. `blacklist.RSA-1024`, `blacklist.RSA-2048`, `blacklist.DSA-1024`) listing fingerprints one per line of all known-weak keys for that (keytype, bitsize) combination. **Detection layer only** — the package ships fingerprints, not the recoverable private keys.
- **`openssl-blacklist-extra` Debian package** — additional architectures/keysizes.
- **`ssh-vulnkey` tool** — Debian's canonical checker, ships with the `openssh-blacklist` (or similar) package. Accepts a pubkey or `authorized_keys` file, computes fingerprints, cross-references against installed blacklist files, reports matches. Exact output-format details to be re-verified against current Kali at build time.
- **Precomputed private-key sets** — H D Moore's original release (`debian_ssh_rsa_2048_x86.tar.bz2` et al.) and GitHub mirrors. **Recovery layer** — contains the actual private keys mappable from fingerprints. NOT shipped by any Debian package; requires separate download and installation on attacker.
- **`exploit-db 5632`** — Ruby SSH brute-force tool that iterates a precomputed key set against a target SSH endpoint. Reference implementation of the recovery mechanism.

### Key types affected

- **RSA** — fully affected. Blacklist coverage: RSA-1024, RSA-2048, RSA-4096 typical.
- **DSA** — fully affected. Blacklist coverage: DSA-1024 typical.
- **ECDSA** — did not exist in OpenSSH during the vulnerable window (introduced OpenSSH 5.7, 2011).
- **Ed25519** — did not exist in OpenSSH during the vulnerable window (introduced OpenSSH 6.5, 2014).

Handler need only check RSA and DSA keys. `ecdsa-sha2-*` and `ssh-ed25519` keys, if present, are unaffected by Debian PRNG (though may be affected by other vulnerabilities not in scope for this handler).

## The keys-don't-move-on-upgrade insight (critical, easily missed)

**Design principle governing this handler's structure:**

SSH keys generated by an affected Debian OpenSSL package remain on disk unchanged through openssl package upgrades. A modern box that was Debian etch in 2007 running `openssl 0.9.8c-1`, was upgraded through Debian versions to a modern openssl (`3.x`), but never regenerated its SSH keys, is STILL Debian-PRNG-vulnerable on those keys.

**Consequence for handler design:** the check must be **per-key**, not per-box. A per-box check ("is the target's current openssl in the affected range?") would produce a false-negative on the modern-box-with-legacy-keys case. That case is arguably the more operationally significant one, because legacy-openssl boxes have often been patched or retired into obscurity while modern-openssl boxes may quietly retain the weak keys admins forgot to rotate.

**Handler must therefore fire on every enumerated pubkey of type `ssh-rsa` or `ssh-dss`, regardless of the target's current openssl version.** No per-box precondition gates the check.

This is the primary reason [[SSH Keys]] is the correct structural home rather than LPEC Step 16 (Narrow-applicability vectors). Step 16 sub-blocks share a shape: quick per-box precondition → route on hit → INAPPLICABLE on miss. Debian PRNG has no clean per-box quick precondition. Applying one to fit the Step 16 shape would produce false-negatives on the operationally-important case.

## Design decisions — rationale-preserving

### Why this is a new handler in [[SSH Keys]] Step 2, not a new walkthrough

**Consideration:** is Debian PRNG's exploit chain divergent enough from existing SSH key handlers to warrant a separate walkthrough per Vault_Strategy's "Walkthrough split-vs-unify rule"?

Sub-step mapping vs the existing plain private-key handler:

|Sub-step|Debian PRNG|Plain private-key handler|
|---|---|---|
|Enumeration (Step 1)|Same script, same run|Same script, same run|
|Marker consumption (which markers this handler picks up at Step 2)|Public-key markers (`SSH_AUTHKEYS`, `SSH_PUBKEY`)|Private-key markers (`SSH_PRIVKEY`, `SSH_PEM_OUTLIER`)|
|Extract fingerprint from key material|New sub-step|Not needed (already have private key)|
|Blacklist lookup|New sub-step|Not needed|
|Retrieve private key|New sub-step (from precomputed set)|Not needed (already have it)|
|Identify SSH target user|New sub-step (sshd_config AuthorizedKeysFile derivation)|Existing path-based dispatch|
|SSH-in|Same shape|Same shape|
|Verify with `id`|Same shape|Same shape|

Three sub-steps new to the mechanism; two shared (SSH-in + verify). Enumeration is shared — one `ssh_enum.sh` run produces both marker sets.

**Initial (incorrect) reasoning attempted during the session:** apply Vault_Strategy's split-vs-unify rule at the walkthrough level. Argue "3 of 5 sub-steps diverge — this is a propagating fork — therefore Debian PRNG earns a separate walkthrough."

**Correction:** the split-vs-unify rule applies to walkthrough-level forks. Existing [[SSH Keys]] handlers (agent hijack, plain private-key, encrypted private-key, config) are each mini-chains with their own extract-and-authenticate mechanism — the walkthrough scope encompasses "SSH key material dispatch" and that already spans private and public key material. Debian PRNG is the same shape as those existing handlers: a mini-chain, a peer handler in Step 2. This is a handler-level fork within a single walkthrough, NOT a walkthrough-level fork. Correct precedent is the handler-in-walkthrough pattern already established in [[SSH Keys]].

### Why not a Shared Concept (like [[GTFOBins Cross-Reference]])

**Consideration:** [[GTFOBins Cross-Reference]] is a walkthrough invoked as a shared subroutine by [[Sudo Shell Escape]] and [[SUID Known Exploits]]. Could Debian PRNG be similarly organised — its own file, invoked as a subroutine by [[SSH Keys]]?

**Rejected.** [[GTFOBins Cross-Reference]] qualifies as a Shared Concept because it has (a) multiple actual callers and (b) sits at a different abstraction layer — it is a technique-catalogue-mechanism, not a peer PrivEsc vector. Debian PRNG at build time has one committed caller — this handler within [[SSH Keys]]. Plausible future callers exist in theory (post-root Credential Extraction, Lateral Movement) but neither exists yet. Under Vault_Strategy's build-when-encountered convention, speculative multi-caller infrastructure is not earned. If Debian PRNG's mechanism proves reusable when other callers are built, refactor to Shared Concept at that time.

### Why not LPEC Step 16 — Narrow-applicability vectors

**Consideration during session:** Debian PRNG is exotic-tier — could it group with Step 16's other narrow-applicability vectors (Big UID polkit, DOAS, ifcfg-*)?

**Rejected.** Step 16 sub-blocks share a shape: quick per-box precondition → route to walkthrough on hit → INAPPLICABLE on miss. Debian PRNG has no clean per-box precondition (see "The keys-don't-move-on-upgrade insight" above — check is per-key, not per-box). Any per-box gate would produce false-negatives on the modern-box-with-legacy-keys case. Correct structural home is [[SSH Keys]] which already handles per-key dispatch through its enum-and-handler pattern.

### Why the handler is inline-self-contained, not cross-referencing plain private-key handler

**Consideration:** the Debian PRNG chain ends with SSH-in + verify. Those two sub-steps are structurally identical to the tail of the existing plain private-key handler. Could the new handler cross-reference the plain private-key handler for the SSH-in step, avoiding duplication?

**Rejected — spaghetti.** Intra-walkthrough cross-reference between peer handlers creates a routing pattern where handler A hands off to handler B mid-execution. Under operational pressure the operator loses track of "which handler am I in, what's the exit condition." Correct form is inline duplication of the SSH-in step (two lines) in the new handler. Vault_Strategy accepts minor duplication cost as trade for handler self-containment.

### Handler position in Step 1 priority list

Reasoning from cost-adjusted yield.

- **Cost per pubkey check:** ~seconds (fingerprint extract + local grep against blacklist file).
- **Yield rate per box** (any enumerated pubkey being Debian-PRNG-weak): near-zero on modern targets; non-zero on legacy CTF/HTB/lab targets and Debian-family production boxes with unrotated legacy keys.

**Comparison against neighbouring handlers:**

- **Plain private-key handler:** higher absolute yield (direct SSH with known key), similar per-attempt cost. Should run first.
- **Encrypted private-key handler (`ssh2john` + `john`):** moderate yield, minutes-to-hours per key depending on wordlist. Slower than Debian PRNG check.

Cost-adjusted yield (yield-per-second-of-work) favours Debian PRNG _before_ encrypted private-key handling. Even where absolute yield is lower, per-second yield is better because the blacklist check is a fast local grep.

**Recommended position (deferred to handler build time — NOT applied this session):** insert the new handler's markers between the plain and encrypted private-key handler entries in the Step 1 priority list. Concretely:

```
- `SSH_AGENT_HIJACKABLE: <sock> (owner=<owner>)` → Agent hijack handler.
- `SSH_PRIVKEY: <file> [plain] [<fp>]` → Private key handler — plain.
- `SSH_PEM_OUTLIER: <file> [plain] [<fp>]` → Private key handler — plain.
- `SSH_AUTHKEYS: <file>` (indented pubkey lines follow) → Public key handler — Debian PRNG lookup.
- `SSH_PUBKEY: <file>` → Public key handler — Debian PRNG lookup.
- `SSH_PRIVKEY: <file> [encrypted] [<fp>]` → Private key handler — encrypted.
- `SSH_PEM_OUTLIER: <file> [encrypted] [<fp>]` → Private key handler — encrypted.
- `SSH_CONFIG: <file>` → Config handler.
- ... (informational tier below unchanged)
```

**`SSH_AUTHKEYS` and `SSH_PUBKEY` move OUT of the informational tier into the actionable tier.** Their previous "informational" designation ceases to apply once the handler is built. The applied F&Rs this session preserve the informational designation as a fallback ("if handler unbuilt or Debian PRNG doesn't apply") — the reordering is a build-time task to be executed when the handler body is built.

### SSH_AUTHKEYS pubkey vs SSH_PUBKEY pubkey — value distinction (critical for handler priority within itself)

**SSH_AUTHKEYS pubkey compromise = direct value.**

The pubkey line sits inside an `authorized_keys` file that sshd will consult for some SSH login principal. If recovered private key succeeds against that principal's SSH endpoint, direct login as that principal. On this box. Target derivation from the file path per the sshd_config-aware logic below.

**SSH_PUBKEY (standalone) pubkey compromise = contingent value.**

The pubkey is a standalone `.pub` file — typically `~/.ssh/id_rsa.pub` (paired with an on-disk private key) or an archived copy. The recovered private key doesn't have an automatic target on this box. Value paths:

- **Pivot-to-other-host:** recovered key may authenticate on some other host — needs `~/.ssh/config` `IdentityFile` cross-refs or `known_hosts` entries to give pivot targets. Non-trivial follow-up work.
- **Recover a locally-unreadable private key:** if `SSH_PRIVKEY_DENIED` fired on the same-directory paired private key, recovering that private key via Debian PRNG bypasses the readability restriction. Uncommon corner case.

The "corresponding on-disk private key" path is a **corner case, not the default value path**. Do not assume standalone `.pub` files have on-disk paired private keys, and do not derive SSH targets from standalone `.pub` file ownership on that assumption. Standalone-pubkey value derives primarily from pivot-to-other-host mechanisms.

**Handler priority ordering within itself:** SSH_AUTHKEYS pubkeys first (direct target), SSH_PUBKEY pubkeys second (contingent target).

### Target-user derivation from SSH_AUTHKEYS path — the correct form

**Critical, and reasoning went through wrong forms during the session. Final correct form preserved here to prevent regression on future build.**

**WRONG (documented to prevent regression):** "the file owner (via `stat -c %U`) is the SSH login target." Rationale for why this is wrong: file ownership on disk is not what sshd uses to determine "who does this authorized_keys file authenticate?" — sshd uses the file's PATH under its `AuthorizedKeysFile` directive, which links path to principal via a substitution pattern.

**Also WRONG (documented to prevent regression):** "the pubkey line's `<owner>@<host>` comment field is the SSH login target." Rationale: the comment field is a free-text label written by the key generator and has no authentication semantic. `<owner>@<host>` in the comment could be entirely different from the principal that sshd will authenticate the key for.

**CORRECT:** The SSH login target for a pubkey inside an `authorized_keys` file is determined by which principal's SSH login sshd will consult that file for. Governed by `sshd_config`'s `AuthorizedKeysFile` directive.

Three configuration shapes:

1. **Default `AuthorizedKeysFile .ssh/authorized_keys`:** sshd consults `~<user>/.ssh/authorized_keys` when authenticating `ssh <user>@host`. Path is relative to the login target's home directory. **Target user = the user whose home directory the file lives in.** File on-disk owner is irrelevant to sshd's authorization decision (sshd may check ownership for security reasons but that's protection, not identity determination).
    
2. **Non-default per-user `AuthorizedKeysFile /etc/ssh/authorized_keys/%u`:** sshd substitutes `%u` = login target at authentication time. **Target user = derived from the `%u` substitution — the filename encodes the target.** Files typically owned by root; owner is again irrelevant to authorization.
    
3. **Non-default shared `AuthorizedKeysFile /etc/ssh/authorized_keys_common`** (rare, but real — e.g. a bastion server where multiple named users all authenticate against a single shared authorized_keys pool for operational simplicity): **target user is ambiguous from the file alone** — sshd will accept the pubkey for any user whose login triggers consultation of this file. Handler must loop candidate users.
    

**Real-world observation preserved during session:** on many production servers, multiple named users (`user_one`, `user_two`, `user_three`) may all authenticate as a shared operational user (e.g. `ubuntu`, `ec2-user`, `admin`) whose `~/.ssh/authorized_keys` file contains all their pubkeys. In this common case, the file lives under `/home/ubuntu/.ssh/authorized_keys`, so per-rule-1 the target user = `ubuntu`. Multiple humans may share the `ubuntu` login. Handler treats target as `ubuntu` — mapping to specific humans is out of scope for LPEC.

**Handler algorithm for target-user derivation:**

```

1. Read /etc/ssh/sshd_config (and /etc/ssh/sshd_config.d/*.conf if includes are present).
2. Find AuthorizedKeysFile directive(s). May be absent (→ default), single, or multiple.
3. Match the SSH_AUTHKEYS marker's file path against the directive pattern(s):  
    a. Default pattern (.ssh/authorized_keys or no directive) — path is ~<user>/.ssh/authorized_keys → path-derived target = <user>.  
    b. Directive contains a `%u` or `%h` token → sshd substituted the token at auth time to produce this path. Reverse the substitution: extract the substring corresponding to `%u` (username) from the marker path. Path-derived        target = extracted username. Example: directive `AuthorizedKeysFile /etc/ssh/authorized_keys/%u`, marker path `/etc/ssh/authorized_keys/alice` → path-derived target = alice.  
    c. Directive contains no `%u` or `%h` token (hardcoded path, e.g. `AuthorizedKeysFile /etc/ssh/authorized_keys/team_shared`) → sshd reads the same file for every user's login attempt. Path components are not target users.         Path-derived target absent; candidate loop only.
    d. Path corresponds to no `AuthorizedKeysFile` directive at all — the file exists on disk but sshd never reads it at authentication time (orphan file). Path-derived target absent; local candidate loop skipped (guaranteed          to fail). Route the recovered private key to the SSH_PUBKEY branch's pivot-fallback logic — material may still authenticate on another host via known_hosts / config `IdentityFile` cross-refs.
4. If sshd_config unreadable → assume default AuthorizedKeysFile → derive per (a).
5. If sshd_config indicates non-default and path doesn't match cleanly to a user → path-derived target absent; candidate loop only.

Attempt order per Debian-PRNG-recovered private key:

1. Try `root` first — trivial cost, terminal-on-hit. Root's authorized_keys may contain the same pubkey (uncommon but non-zero); root SSH login may accept the key subject to `PermitRootLogin`.
2. Try path-derived target (if any, from step 3 above).
3. Candidate loop over all interactive users:  
    `awk -F: '($3==0||$3>=1000)&&$7!~/(nologin|false)/{print $1}' /etc/passwd`  
    Iterate `ssh <candidate>@localhost` until one succeeds, `Permission denied (publickey)` exhausts, or all candidates rejected.
4. All attempts exhausted → next pubkey line.

Rationale: root-first ordering optimises for probability of reaching root (OSCP framing — root ends the box; a lateral user foothold means continuing work). Cost of a single failed root ssh attempt is trivial; missing a root path because a lower-privilege attempt succeeded first is a materially bad outcome.  

```

### Fingerprint format — what to feed the blacklist

- **SSH pubkey fingerprint (modern OpenSSH default):** `SHA256:<base64>` — output of `ssh-keygen -lf <keyfile>` on modern OpenSSH. 43 base64 characters after the `SHA256:` prefix.
- **SSH pubkey fingerprint (legacy MD5):** `MD5:<hex>` — output of `ssh-keygen -E md5 -lf <keyfile>`. Colon-separated hex bytes after the `MD5:` prefix.
- **Debian openssl-blacklist file format:** NOT the SSH pubkey fingerprint. Debian's blacklist uses a truncated SHA1 of a normalised representation of the public modulus, not the standard SSH SHA256 fingerprint of the pubkey. `ssh-vulnkey` handles this format conversion internally.

**Handler consideration — fingerprint format mismatch is a real gotcha.** Two implementation options at build time:

- **Preferred: use `ssh-vulnkey` directly.** It handles the format conversion; simpler at handler level; requires `ssh-vulnkey` present on attacker (typically packaged with `openssl-blacklist` or `openssh-blacklist` — verify on current Kali at build time).
- **Fallback: implement the Debian blacklist hash computation manually** via `openssl` parse-and-hash. More portable but more error-prone; consult `ssh-vulnkey` source for the exact algorithm.

Recommended at build time: use `ssh-vulnkey`. If absent on attacker, install `openssl-blacklist` package (which typically pulls it in as a dependency).

### Attacker Toolchain — two-part setup, both required

Detection alone is not sufficient. Recovery requires the actual private keys, which come from a separate source.

- **Detection layer (fingerprint blacklist):** Debian packages `openssl-blacklist` + `openssl-blacklist-extra`. On Kali, verify preinstall status with `dpkg -l openssl-blacklist openssl-blacklist-extra 2>/dev/null`; install if absent via `sudo apt install openssl-blacklist openssl-blacklist-extra`. Ships fingerprint files at `/usr/share/openssl-blacklist/blacklist.<KEYTYPE>-<BITS>`.
- **Recovery layer (private key set):** H D Moore's precomputed private key archives. NOT shipped by any Debian package. Historical release names include `debian_ssh_rsa_2048_x86.tar.bz2` and variants for other architectures/keysizes. Available on various GitHub mirrors (verify current sources at build time — the original DoxPara URL from 2008 may be defunct). **Requires separate download and installation at a documented convention location on attacker** — proposed default `/opt/debian-prng-keys/` with subdirectories per (arch, keytype, keysize). Final layout decision deferred to build time.

Both are prerequisites for handler execution. [[Attacker Toolchain]] entry needs to cover:

- Detection layer install and verification.
- Recovery layer download source (mirror URL captured at build time) and installation location.
- Layout of `/opt/debian-prng-keys/` (or chosen equivalent) sufficient for handler to locate the private key matching a given fingerprint.
- Completeness verification — does the installed set cover the fingerprint that matched?

## `ssh_enum.sh` extensions required

Current `~/scripts/ssh_enum.sh` was designed with private-key enumeration as primary. Two gaps in public-key coverage must be closed for the Debian PRNG handler to work canonically. Neither is applied at time of writing.

### Extension 1 — wide pubkey pass

Current wide pass (`--wide` argument) greps for `^-----BEGIN [A-Z ]*PRIVATE KEY-----` only (`ssh_enum.sh` line 295 at time of writing). Pubkeys outside standard SSH directories are not surfaced — e.g. pubkeys embedded in backup tarballs, config-management drops, dev-repo checkout examples, container image layers.

**Extension:** in addition to the private-key wide grep, run a parallel wide grep for pubkey line formats, filtered to `ssh-rsa` and `ssh-dss` (the only Debian-PRNG-vulnerable types):

```
grep -lE "^(ssh-(rsa|dss))"
```

Emit new marker: `SSH_PUBKEY_OUTLIER: <file>` (parallel to `SSH_PEM_OUTLIER` for private keys). Same OPSEC caveats as the existing wide private-key pass: long-running `find` visible in `ps`; high `open`-syscall volume detectable by auditd/EDR; behind `--wide` gate.

**Filter rationale:** deliberately exclude `ecdsa-sha2-*` and `ssh-ed25519` — those key types cannot be Debian-PRNG-vulnerable (didn't exist during vulnerable window). Excluding them reduces marker noise.

### Extension 2 — sshd_config `AuthorizedKeysFile` parsing

**Coverage gap acknowledged:** this extension does not cover `AuthorizedKeysCommand` — a separate sshd_config directive that specifies a program returning pubkeys dynamically (LDAP, cloud metadata, centralized auth). Dynamic-source keys never touch disk; file-based enumeration cannot see them. Debian PRNG detection against dynamic sources would require intercepting command output — out of scope. If `AuthorizedKeysCommand` is set on target, ssh_enum.sh's SSH_AUTHKEYS coverage is incomplete for that box. Consider emitting an informational `SSH_DYNAMIC_PUBKEY_AUTH: <command>` marker to signal the gap. Decide at build time.

Current `ssh_enum.sh` builds `SSH_DIRS` from `/etc/passwd` home directories (`ssh_enum.sh` lines 159-170 at time of writing) — it looks under each interactive user's `~/.ssh/`. Non-standard `AuthorizedKeysFile` locations (`/etc/ssh/authorized_keys/%u`, `/etc/ssh/authorized_keys_common`, other patterns) are entirely missed.

**Extension:** read `/etc/ssh/sshd_config` (plus `/etc/ssh/sshd_config.d/*.conf` if `Include` directives are present in the base file), parse `AuthorizedKeysFile` directive(s), expand `%u` and `%h` tokens against the interactive-user list from `/etc/passwd`, and add resulting paths to enumeration scope.

Emit for each non-default path: `SSH_AUTHKEYS: <expanded-path>` if readable (with indented pubkey lines beneath, matching the existing `SSH_AUTHKEYS` marker shape), `SSH_AUTHKEYS_DENIED: <expanded-path>` if not readable.

**Token semantics** (per `sshd_config(5)`):

- `%u` — username of the authenticating user.
- `%h` — home directory of the authenticating user.
- `%%` — literal `%`.
- Other tokens — ignore (do not error on).

**Edge cases to handle:**

- `AuthorizedKeysFile` may appear multiple times in `sshd_config`; sshd reads them all.
- `AuthorizedKeysFile none` — explicit disable of pubkey authentication → skip enumeration for this target user.
- `Include /etc/ssh/sshd_config.d/*.conf` in base file — must recursively process included files (may override or supplement `AuthorizedKeysFile`).
- `sshd_config` unreadable to foothold → fall back to standard SSH_DIRS enumeration only (existing behaviour); do not error.

### Regression tests required

## Proposed handler structure (paste-ready when built)

Insert into [[SSH Keys]] Step 2 in place of the current stub. Existing precedents referenced: plain private-key handler (SSH-in shape, `HostKeyAlgorithms=+ssh-rsa` fallback flags, verification with `id`); Writable Passwd Step 5 (explicit `id` verification per Vault_Strategy line 142).

```markdown
### Public key handler — Debian PRNG lookup

**Applies to markers:** SSH_AUTHKEYS (each indented pubkey line beneath the marker) and SSH_PUBKEY (standalone `.pub` file contents).

**Preconditions:**

- Attacker has `openssl-blacklist` and `openssl-blacklist-extra` packages installed (provides `ssh-vulnkey` and the blacklist files), OR equivalent blacklist files at known path. See [[Attacker Toolchain]] Debian PRNG entry.
- Attacker has H D Moore's precomputed private key set installed at documented path (default `/opt/debian-prng-keys/`). See [[Attacker Toolchain]] Debian PRNG entry.
- Only apply to pubkey lines starting with `ssh-rsa` or `ssh-dss`. Skip `ecdsa-sha2-*` and `ssh-ed25519` — not Debian-PRNG-vulnerable.

**Design principle — check every pubkey regardless of target's current openssl version:** SSH keys generated by an affected Debian OpenSSL package persist unchanged through openssl upgrades. A fully-patched modern box may still carry legacy weak keys in authorized_keys files. Handler fires on all enumerated pubkeys of type ssh-rsa or ssh-dss; no per-box gate.

**Priority within handler:** SSH_AUTHKEYS pubkeys first (direct target), SSH_PUBKEY pubkeys second (contingent target).

##### SSH_AUTHKEYS branch — direct target

For each pubkey line indented beneath `SSH_AUTHKEYS: <file>` (skip lines whose keytype token is not `ssh-rsa` or `ssh-dss`):

On **attacker**:

`echo '<pubkey-line>' > /tmp/candidate.pub`

`ssh-vulnkey /tmp/candidate.pub`

- Output indicates COMPROMISED / blacklisted key → key is Debian-PRNG-weak. Proceed to key retrieval.
- Output indicates key not in blacklist → key not weak. Next pubkey line.
- `ssh-vulnkey: command not found` → openssl-blacklist package not installed on attacker. See [[Attacker Toolchain]].

Retrieve corresponding private key from precomputed set. Exact command depends on the layout chosen at Attacker Toolchain build time. Placeholder shape:

`find /opt/debian-prng-keys/ -name '<fingerprint-derived-filename>' -o -exec grep -l <fingerprint> {} \;`

Copy located private key to working path:

`cp <located-key> /tmp/recovered.key && chmod 600 /tmp/recovered.key`

Derive target user from the `SSH_AUTHKEYS: <file>` path per sshd_config-aware logic (see design note "Target-user derivation" section). Concretely:

- Path matches `/home/<user>/.ssh/authorized_keys` → target `<user>`.
- Path matches non-default sshd_config `AuthorizedKeysFile` pattern with user-token substitution (e.g. `/etc/ssh/authorized_keys/<name>`) → target from the substitution.
- Path matches shared-file pattern → candidate loop.

Candidate loop:

`awk -F: '($3==0||$3>=1000)&&$7!~/(nologin|false)/{print $1}' /etc/passwd`

Attempt order: root first, then path-derived target, then candidate loop over interactive users. Rationale: root-first ordering optimises for probability of reaching root — cost of a failed root ssh attempt is trivial, upside is terminal.

For each target `<user>` in order [root, path-derived, candidate loop]:

On **target**:

`ssh -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa -i /tmp/recovered.key <user>@<target-host>`

Then verify:

`id`

- `uid=0(...)` → root authority achieved. Done.
- `uid=<non-zero>(...)` → lateral foothold as `<user>`. Re-enter [[Linux Privilege Escalation Checksheet]] from new context.
- `Permission denied (publickey)` → target user rejected; try next target.
- `Too many authentication failures` → retry with `-o IdentitiesOnly=yes -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa -i /tmp/recovered.key`.
- All targets exhausted → next pubkey line.

##### SSH_PUBKEY branch — contingent target

For each `SSH_PUBKEY: <file>` marker (skip if the file's first-line keytype is not `ssh-rsa` or `ssh-dss`):

On **target**:

`cat <file>`

Copy the pubkey line output.

Then follow the SSH_AUTHKEYS branch's blacklist-check and key-retrieval steps against the copied pubkey.

Target-user derivation is contingent for standalone pubkeys — the file path does not encode an SSH principal. Consult in priority order:

- Cross-reference `SSH_CONFIG` output's `IdentityFile` entries — if this pubkey's private key is referenced by a config `IdentityFile` line, the config's `HostName` and `User` fields give the pivot target.
- Cross-reference `SSH_KNOWNHOSTS` output for host pivot targets.
- Fall back to candidate loop: attempt `ssh <candidate>@localhost` for each interactive user, then `ssh <candidate>@<known-host>` for each known-hosts pivot target.

SSH-in and verification as per SSH_AUTHKEYS branch above.
```

**Notes on the paste-ready structure:**

- Uses `ssh-vulnkey` for detection assuming Debian package convention. Verify output format on current Kali at build time and update the "output indicates COMPROMISED" phrasing to match the tool's actual output.
- Uses a placeholder command for private-key retrieval because the layout of the installed precomputed set varies across mirrors and installation choices. At Attacker Toolchain build time, decide on a canonical layout under `/opt/debian-prng-keys/` (or chosen equivalent) and update the retrieval command to match.
- SSH-in uses `HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa` fallback flags. Necessary because Debian-PRNG-weak keys are `ssh-rsa` or `ssh-dss`, both of which modern OpenSSH clients disable by default.
- Verification with `id` follows Vault_Strategy line 142 (explicit `id` check, `uid=0(...)` output-keyed branch).
- SSH_AUTHKEYS branch has `ssh` running from target (matching existing plain private-key handler's "from target first" preference). SSH_PUBKEY branch: the `cat <file>` runs on target, then attacker executes ssh — because standalone pubkey pivot may target another host reachable from attacker rather than localhost.

## Alternative approaches considered and rejected

Preserved so future build does not re-litigate.

1. **LPEC Step 16 — Narrow-applicability vector.** Rejected: no clean per-box precondition; check must be per-key; forcing per-box gate produces false-negatives on modern-box-with-legacy-keys.
2. **Separate walkthrough `[[Debian PRNG Public Key Compromise]]` per V_S split-vs-unify rule.** Initial claim was an overclaim of the rule's scope — V_S split-vs-unify applies to walkthrough-level forks; this is a handler-level fork within an existing walkthrough. Rejected in favour of the handler-in-existing-walkthrough pattern already established in [[SSH Keys]].
3. **Shared Concept (like [[GTFOBins Cross-Reference]]).** Rejected: only one committed caller today; multi-caller reuse infrastructure not earned per V_S build-when-encountered. Revisit if/when a second real caller appears (e.g. post-root Credential Extraction or Lateral Movement layers when built).
4. **Handler that cross-references plain private-key handler for the SSH-in step.** Rejected as spaghetti: intra-walkthrough cross-reference between peer handlers. Correct form is inline duplication of the SSH-in step (~2 lines) in the new handler; Vault_Strategy accepts this minor duplication cost as a trade for handler self-containment.
5. **Per-box openssl version check as the primary gate.** Rejected: fails the keys-don't-move-on-upgrade case (see principle above). Would be a critical false-negative on the operationally-important case.
6. **Fingerprint check on public key by hashing the raw pubkey material directly (bypassing the Debian-blacklist-specific format).** Rejected: the Debian blacklist files use a specific truncated-SHA1-of-modulus format, not any standard SSH fingerprint format. Matching against them requires the format conversion — either use `ssh-vulnkey` which handles it, or reimplement the exact conversion. Direct SHA256 hashing of pubkey material does not match the blacklist.
7. **Split `ssh_enum.sh` into separate private-key and public-key enumeration scripts.** Rejected: enumeration paths (SSH_DIRS iteration; wide filesystem pass) are shared between private and public key discovery. Splitting would double the enumeration cost per box. Correct form is extension of the existing script with additional filters and marker types.
